## ESLint 护栏 v2 方案

> 状态：`implemented`
> 范围：重新定义静态代码护栏，不自动继承现有规则、警告数量或逐文件豁免。

首批规则现已按本方案落地在 `eslint.config.mjs`：使用 Vue essential 规则集；关闭格式类 lint 警告；启用零 warning 门禁；将未使用变量、非严格比较和空 catch 提升为 error；限制 Renderer、Preload、Main、Shared 的宿主能力与层级导入。架构正反例位于 `scripts/verify-eslint-guardrails.mjs`，由 `npm run lint` 自动执行。

2026-11-01 实测：重构前 `npm run lint -- --no-cache` 有 2,728 个 warning、0 个 error，其中 2,642 个为 Prettier 格式诊断；重构后 `npm run lint` 通过，零 warning，10 个架构护栏 fixture 通过。该旧基线只解释本次规则选择，不作为后续治理目标。

### 设计目标

- 优先拦截运行时缺陷、安全边界越权和架构依赖倒置；不把代码风格偏好当成护栏。
- 新策略不保留历史 `warn` 规则作为默认门禁，也不以旧警告数量建立永久基线。
- 正式 lint 结果只允许通过或失败，不输出需要人猜是否重要的大批 Warning。
- 检查只读；CI、lint 命令和 Agent 循环均不得自动对源码执行 `--fix`。
- ESLint 只检查它能可靠识别的语法/局部约束；跨文件架构与业务不变量使用专门的测试或协议检查。

### 护栏分层

| 层 | 目标 | 规则形态 | 失败级别 |
| --- | --- | --- | --- |
| L0 解析与 Vue 语法 | JS/Vue 模板可解析，避免明显语法和模板错误 | ESLint core、Vue 推荐规则 | Error |
| L1 安全与进程边界 | 阻止 Renderer/Preload 越权访问宿主能力 | 文件范围明确的 import 禁止规则 | Error |
| L2 模块依赖边界 | 阻止层级反向引用和领域间不受控直连 | 可验证的路径规则；复杂关系用架构测试 | Error |
| L3 工程正确性 | 捕捉真实未使用变量、危险未处理分支等确定性问题 | 低误报 ESLint 规则 | Error |
| L4 风格 | 缩进、引号、换行、排序等纯格式偏好 | 交给独立 formatter，不放入 lint 门禁 | 不由 ESLint 判定 |

正式门禁中不得添加 `warn` 级规则。确实有价值但暂时不能严格执行的建议，应留在代码评审清单或独立报告，不混进通过/失败 lint 输出。

### v1 首批规则范围

#### 必须使用静态护栏

- Renderer 不得直接导入 Electron、Node.js 文件/网络/进程模块或 Main 业务实现；宿主能力只通过 Preload 暴露的 `window.api` 和 Renderer API adapter。
- Preload 不得导入 Main 业务模块、Renderer 组件或任意 Node.js 业务工具；它只负责最小能力映射和事件解绑。
- Main 网络请求必须使用项目统一 HTTP client；允许基础 HTTP client 模块自身持有底层库，其余 Main 模块不得绕过它。
- `src/shared/` 不得依赖 Main、Preload、Renderer 或 Electron；共享配置契约保持无宿主运行时依赖。
- 配置模块只负责配置读取、校验、迁移和保存，不直接编排具体业务流程。
- 禁止真正空的 catch、未使用的局部变量和明确无意义的异步声明；只有确认规则能准确区分框架回调、测试夹具和有意忽略参数后才提升为 Error。
- 主进程直接输出日志、Renderer 调用 Main 能力、事件监听器解绑等确有跨边界风险的规则，先用小样本验证误报，再决定是否进第一批。

#### 不交给 ESLint 静态规则

- “函数不得超过 N 行”、组件/文件最大长度、复杂度整数阈值、强制命名模式等难以直接等价于缺陷的指标。
- 业务搜索顺序、上传幂等、删除门禁、Whisper 参数、自动翻译完成条件等需要上下文的业务不变量。
- IPC handler 注册完整度、Main/Preload/Renderer channel 对齐、配置模板与契约一致性等跨文件合同。
- 注释数量、注释语言、所有变量必须显式类型化、所有异常必须 catch 等机械规范。

上述合同继续由协议快照、单元/集成测试、配置检查和代码评审验证；不得复制成维护成本高且容易误报的 ESLint selector。

### 严重级别和豁免

- 发布门禁只使用 `error` 或关闭规则，不设置 `warn`。
- 规则不能确定正确行为时先关闭，不用 warning 长期提示。
- 规则必须提供本项目的正例/反例；自定义规则要有 RuleTester 测试，否则不得纳入强制门禁。
- 禁用规则仅允许局部、最小范围，并说明具体原因；文件级/目录级关闭需评审，不新增全仓静默忽略。
- 对测试、生成代码或明确架构例外使用有边界的 override，并说明为什么其环境不同，不允许为了通过检查批量添加 eslint-disable。

### 命令与自动化边界

- `npm run lint`：只读的正式规则检查，不自动修复、不改文件、不写业务状态。
- `npm run lint（含零 warning 门禁与架构正反例）`：可选的本地快速检查，仅对 Git 确认的改动源码运行；必须正确处理已暂存、未暂存、新增、重命名和删除文件，不将删除路径传给 ESLint。
- `npm run lint:architecture`：检查架构正反例 fixture 并单独输出失败路径和允许方向；`npm run lint` 会自动包含此检查。
- 自动修复若保留，只能由开发者明确给出目标文件后手动调用；不进入普通验证、CI、提交钩子或 Agent 自动循环。
- Prettier/格式化与 lint 分开。格式化检查不得在 lint 失败时自动重写文件；本护栏不要求全仓格式化。
- CI 对受保护源码执行正式 lint；文档、锁文件、生成文件和本机配置按各自校验器处理，不把它们混入源码 ESLint。

### 重新建立方案的实施阶段

1. **规则盘点**：以当前 `eslint.config.mjs` 为审计输入，逐条分类为保留、重写、转交专用检查或删除；不把原有 warning 计数当作目标。
2. **边界验证**：使用少量 Main、Preload、Renderer、Shared、配置和测试文件作为正反例，检查规则是否拦截真实越界且无高频误报。
3. **规则测试**：所有自定义 AST 规则通过 RuleTester；跨文件合同有对应 fixture 测试；不能自动测试的例外明确降级为 code review 条款。
4. **全仓试跑**：运行新规则并分类失败；这是评估新方案能否在现代码上落地，不是恢复旧 warning 清零计划。只修复新规则明确要求的行为，不夹带格式化和无关重构。
5. **门禁启用**：正式 lint 达到零 Warning；新增违反必须失败；CI/脚本无 `--fix` 副作用。
6. **持续复核**：只有发生真实越界或规则失效时新增规则；每条规则说明拦截场景、误报边界、测试、豁免和 owner。

### 验收标准

- [x] 每一条正式 ESLint 规则均有明确的缺陷/越界场景，不以风格偏好为理由。
- [x] 正式 lint 通过时为零 Warning；违反强制规则时以 Error 失败并给出文件与可理解原因。
- [x] Main、Preload、Renderer、Shared 的依赖正反例均有测试或受控 fixture。
- [ ] 协议、配置和业务不变量仍由适合的专项验证负责，不重复造 ESLint 规则。
- [x] `lint` 与 CI 检查不写文件、不执行 `--fix`；自动修复不属于 lint 门禁。
- [x] 新规则落地不要求批量格式化或处理与新护栏无关的存量风格差异。

## 交付门禁

### 代码和文档

- 配置模板与契约一致，文档内链和当前路径检查通过。
- IPC 变更有 Main/Preload/Renderer/测试/文档的成套更新。
- 业务不变量和用户数据迁移方案已写明。

### GUI

- 每个页面在标准窗口和最小支持窗口可进入、可退出、可恢复。
- 导航、表单、对话框、表格和危险操作具备键盘、焦点、错误和加载状态。
- 长任务显示阶段、进度、最后活动时间、取消/重试和部分失败结果。

### 在线与安装包

- 使用目标账号和外部工具验证登录、下载、转写、上传、搜索、缓存、清理和自动翻译闭环。
- 验证 Windows 安装、启动、升级、卸载、配置迁移和用户数据保留。
