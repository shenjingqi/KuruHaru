# 侧边栏导航重构方案（信息架构 + 交互优化）

> 状态: ✅ 已实现（Phase 1 + Phase 2 + Phase 3）
> 创建时间: 2026-03-04
> 关联代码: `src/renderer/src/App.vue`

## 背景

当前左侧导航在 `App.vue` 中采用平铺菜单，一级入口数量已达到 12 个，仅“数据清理”有子菜单，导致以下问题：

1. 导航密度过高，首屏识别成本上升。
2. 高频功能与低频工具混排，用户决策路径变长。
3. 后续继续加功能时，侧边栏可扩展性不足。

## 目标

1. 在不改变核心业务能力的前提下，降低左侧导航视觉拥挤度。
2. 按“任务流”重组入口，减少用户在功能间来回跳转的成本。
3. 形成可扩展结构，后续新增功能优先落入既有分组而非继续平铺。

## 非目标

1. 本方案阶段不改动各业务模块内部逻辑。
2. 本方案阶段不引入全新页面，仅重构导航层与路由映射关系。

## 重构方案（V1）

### 1) 导航结构重组：平铺改为分组折叠

保留“仪表盘”作为独立一级入口，其余功能按场景分组，默认只展开一个高频分组。

建议结构：

- 一级固定：`仪表盘`
- 分组 A（高频工作流）：`上传字幕`、`音声翻译`、`最近上传`
- 分组 B（数据与检索）：`数据清理（本地/云端）`、`高级搜索`、`RJ筛选`、`汉化列表`、`工具箱`
- 分组 C（Telegram）：`TG搜索Bot`、`RJ重复检测`
- 分组 D（系统）：`设置`

收益：

- 首屏可见项显著减少，减少“菜单墙”感。
- 功能定位从“记名称”变为“先找分组再找功能”。

### 2) 交互策略：保留现有点击习惯，新增轻量增强

1. 记忆展开状态：分组展开/折叠状态持久化（本地存储）。
2. 当前定位强化：激活项高亮 + 所属分组自动展开。
3. 收起态优化：侧边栏收起时展示分组悬浮面板，避免完全盲点选。

### 3) 可扩展约束（后续新增功能的落位规则）

1. 新功能优先归入既有分组，禁止新增平铺一级入口。
2. 仅当某分组超过 6 项时，才允许拆分新分组。
3. 保持“一级固定入口 ≤ 2，分组数 ≤ 5”的上限。

## 实施计划

### Phase 1（结构重组，低风险）

- [x] 抽离导航配置：将 `menuItems` 从 `App.vue` 提炼为结构化分组配置。
- [x] 重构渲染：`nav-list` 支持“分组标题 + 子项列表 + 折叠状态”。
- [x] 保持兼容：保留现有 `currentView` 与 `activeComponent` 映射，不改业务组件。

### Phase 2（交互增强，中风险）

- [x] 增加展开状态持久化（localStorage）。
- [x] 实现“点击当前项时自动展开所属分组”。
- [x] 收起态增加悬浮分组菜单。

### Phase 3（体验打磨，可选）

- [x] 为高频入口提供“快捷区/最近访问”能力（最多 3 项）。
- [x] 优化动画与间距，确保长菜单滚动时可读性。

## 验收标准

- [x] 默认展开时，首屏可见导航块明显减少（从 12 个平铺项变为“1 一级 + N 分组”）。
- [x] 任一现有页面可在不超过 2 次点击内到达。
- [x] 侧边栏收起/展开、分组折叠/展开、页面跳转均无状态错乱。
- [x] `currentView` 对应的页面渲染与标题显示行为与现状一致。

## 风险与应对

1. **风险**：重构后用户短期不适应分组入口。  
   **应对**：默认展开高频分组，并保留图标与原命名，降低学习成本。
2. **风险**：分组状态与当前页面状态不同步。  
   **应对**：以 `currentView` 作为单一真相源，分组展开状态仅作 UI 补充状态。
