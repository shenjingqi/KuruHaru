## 背景

当前项目已出现典型“核心文件过载”信号，导致检索成本、变更冲突概率、回归风险持续上升：

| 文件                                    | 规模（行） | 主要问题                                                                         |
| --------------------------------------- | ---------: | -------------------------------------------------------------------------------- |
| `App.vue`                               |        992 | 壳层布局 + 手工视图映射 + 导航状态 + auth 桥接 + profile 引导 + 大样式块混在一起 |
| `Settings.vue`                          |       1444 | 配置、登录、授权、状态同步职责混合                                               |
| `RecentActivity.vue`                    |       1121 | 过滤、导出、下载、批处理逻辑堆叠                                                 |
| `src/main/modules/asmr-localization.js` |       1809 | 数据抓取、转换、清理、IPC 装配混合                                               |
| `src/main/modules/tg-search-bot.js`     |       1564 | TG 索引/查询/状态与 IPC 混合                                                     |
| `src/main/index.js`                     |        677 | 应用启动编排 + 领域 IPC 注册并存                                                 |
| `src/preload/index.js`                  |        166 | API 面积较宽（多通道混杂，查找成本高）                                           |

同时，对知名 Electron + Vue 项目做结构对比后，结论一致：

- 常见做法是 **薄壳 App + 分域模块**，而不是把导航、业务编排、状态、样式都压在单一入口文件。
- 对“main 文件较大”的项目，成熟实现通常也会把 IPC 注册/封装独立（例如单独 `ipc.ts` 或 domain register）。

## 决策摘要

采用 **“全量拆解（All-in Scope）+ 分波次落地（Wave Delivery）”**。

覆盖口径（本轮全部纳入治理范围）：

- Renderer 页面/组件：`28` 个 `.vue`
- Main + Preload + Renderer 工具脚本：`34` 个 `.js`
- 合计：`62` 个文件全部纳入拆解计划（不是只拆少数大文件）

### 为什么不是“暂不拆”

1. 关键文件规模与职责混杂已经超出可维护舒适区。
2. 当前改动已频繁触发跨文件联动，继续堆积会放大后续返工成本。

### 为什么不是“一次性交付全拆结果”

1. 当前 `App.vue` 仍使用动态组件映射（未引入 router），一次性改造会放大行为回归风险。
2. IPC 与 preload 在现状下仍需要先做“契约冻结 + 适配层收口”。
3. 全量拆解必须“全范围 + 分批验证”，否则无法保证可回滚性。

### 评审阅读顺序（建议）

1. `决策摘要`：确认“全量纳入 + 分波次落地”是否认可。
2. `全量拆解范围分层`：确认 A/B/C 波次与优先级是否符合业务节奏。
3. `分阶段实施计划`：确认每个 phase 的边界和验收条目。
4. `风险与应对` + `回滚策略`：确认失败场景下可控。

## 目标

1. 先把高风险耦合点拆成“可搜索、可定位、可复用”的模块边界。
2. 在不改变用户行为的前提下，降低核心文件复杂度与跨域耦合。
3. 建立后续可持续演进路径（可选 router 化、可选懒加载）。

## 非目标

1. 本轮不做 UI 风格重设计。
2. 本轮不做业务流程语义变更（仅结构性重构）。
3. 本轮不强制引入 `vue-router`（仅在前置拆解稳定后再评估）。
4. 不改变 ASMR 与 TG 远程连接相关 URL、通道语义与流程顺序。

## 重构原则（强约束）

1. **契约优先**：IPC channel 名称与 `window.api.*` 公开方法在阶段内保持兼容。
2. **小步快跑**：单次改动只触达一个清晰边界，避免大爆炸提交。
3. **先拆纯逻辑，再拆视图壳**：先提取 schema/composable/service，再做模板拆分。
4. **每阶段可回滚**：阶段内必须具备独立验收与独立回退点。
5. **组合式分层**：优先按 `state / action / effect` 拆分 composable，页面只保留编排壳层。

### 红线约束（不可变更）

1. **ASMR 远程 URL 不变**：已有远程接口地址、路径、参数语义保持不变。
2. **TG 远程连接流程不变**：登录、鉴权、拉取/同步、下载/上传的流程顺序不变。
3. **仅允许结构性改造**：可迁移代码位置、抽象模块、增加适配层，但不得改变外部网络行为。

## 风险与应对

1. **风险：IPC/Preload 契约漂移**
   - 应对：先做 Phase 0 契约冻结；阶段内只加别名，不直接删旧方法。

2. **风险：拆分后状态同步错位（特别是导航与授权）**
   - 应对：`currentView` 与授权状态保持单一真相源，所有衍生状态从 composable 输出。

3. **风险：重构分支过大，冲突频繁**
   - 应对：按 phase 切分小批次交付，每个 phase 独立验收。

## 统一验收口径（每阶段）

- [x] `lsp_diagnostics`（改动文件）无 error。
- [x] `npm run test` 通过。
- [x] `npm run verify` 通过（lint + build）。
- [x] `npm run verify:protocol` 通过（Protocol Freeze Invariant 守卫）。
- [x] 与现有功能行为一致（以回归清单为准）。
- [x] ASMR 相关远程 URL 与请求语义与基线一致（无协议漂移）。
- [x] TG 远程连接/鉴权/同步流程顺序与基线一致（无流程漂移）。

## 回滚策略

1. 每个阶段单独变更，失败时仅回滚当前阶段文件。
2. 严禁跨阶段混改（防止回滚颗粒度失控）。
3. 若出现链路回归，优先恢复契约层（preload/main IPC）再处理内部结构。
